# SCOPE.md - what this project is allowed to become

Read this before proposing any work. `CLAUDE.md` describes how the code works.
This file decides what gets built. A private working agreement lives in
`.claude/WORKING_AGREEMENT.md` (not tracked in git). Read it too if present.

## 1. What this project is

The M.Sc. final project for the Machine Learning and Data Science program at
Reichman University. Supervisor: Dr. Ben Galili. Deadline: September 2026.

The authoritative spec is `references/MLDS_Feature_Selection.pdf`. Nothing
else defines the requirements.

## 2. Definition of done (the only four tasks)

1. Implement a feature-selection pipeline for high-dimensional data.
2. Compare the results of different feature-selection techniques.
3. Build infrastructure that expedites the process (parallelized feature
   selection).
4. Run the pipeline on a second dataset, not necessarily gene expression.

Deliverables: runnable software driven by a config file, plus a written final
report assessed for academic quality.

**Test for any proposed work: which of the four tasks does it serve?** If the
answer is "none", say so plainly and drop it.

## 3. Target scope of the package

- One config-driven entry point (`python -m featsel.run --config ...`).
- Four selector families behind the existing `selectors/base.py` interface:
  filter (done), embedded, wrapper, and Higher Criticism.
- One shared evaluation harness: cross-validated classification metrics,
  identical protocol for every method, results written to disk as a table.
- Parallelism over the (method x fold x n_features) grid. Joblib first. GPU
  only if a specific method is provably too slow without it.
- Two datasets: SCAN-B, plus one non-biological high-dimensional dataset so
  the project generalizes beyond genomics.
- Figures and tables generated by code, straight into the report.

## 3a. Methodology rules

Non-negotiable, they decide whether the numbers mean anything.

- **Selection inside the fold.** Every selector is fit on the training split
  only, inside the cross-validation loop. Selecting features on the full
  dataset before splitting is leakage and inflates every reported score.
- **Stratified cross-validation**, not a single 80/20 split. One split is too
  noisy to rank methods against each other.
- **Keep PAM50 as five classes.** The proposal names subtype prediction.
  Binarizing it discards the actual problem. Report macro-F1 alongside
  accuracy because the classes are imbalanced.
- **Random-selection baseline.** A selector that picks k features at random is
  the control every other method must beat. Report it in the same table.
- **Runtime and selected-feature count are first-class metrics**, reported
  next to accuracy for every method. They are what makes task 3 measurable.
- **Fixed seeds everywhere**, so results are reproducible.

## 3b. Two open decisions

Both are required by the four tasks and neither is settled yet. Decide them
early, they shape the code and the report.

**The second dataset (task 4).** Requirements: high-dimensional, not gene
expression, publicly available, small enough to iterate on. Candidates worth
checking: text classification with a bag-of-words or TF-IDF vocabulary, a
tabular UCI high-dimensional set, or ResNet embeddings extracted offline from
a small image set. Whatever is chosen goes in `datasets/<name>/` with a config
in `configs/`, extracted by a script outside the package, and gets a section
in the Data chapter.

**Higher Criticism as a selector.** This is the one method that sets the
project apart from a standard method comparison, and it currently has no
implementation. Plan: a `HigherCriticismSelector` in `selectors/`, following
the published Donoho and Jin thresholding formulation, taking per-feature
p-values from a univariate test, sorting them, computing the HC statistic and
selecting the features above the HC threshold. It selects its own feature
count, which makes it interesting to compare against fixed-k methods and
worth calling out in the report. Standard published HC only.

## 4. Explicitly out of scope

- Rewriting the package from scratch. The existing skeleton stays.
- PyPI publishing, `twine`, release engineering, version strategy.
- A plugin architecture, registries, or generalized extension points.
- Optuna or any hyperparameter search beyond a fixed small grid.
- PyTorch integration, deep models, embeddings inside the package. If image
  embeddings are used as the second dataset, extract them offline and feed
  plain CSV files to the pipeline.
- Novel research contributions. This is a comparative study, not a paper.
- Use standard, published Higher Criticism only. No unpublished variants.

## 5. Order of work

Finish the minimum passing project before adding anything.

1. Re-run what exists end to end and establish the real current state.
2. Tasks 1 and 2: pipeline plus method comparison on SCAN-B.
3. Report writing, in parallel from this point on, never left to the end.
4. Task 4: the second dataset.
5. Task 3: parallel infrastructure.

## 6. Working rules

- **Park it, don't argue it.** When an idea fails the four-task test, add a
  dated one-line entry to `docs/ideas.md` and return to the current step.
- **Smallest next action.** End every session with one concrete, finishable
  step.
- **Commit partial work.** Rough plots and ugly tables get committed, not
  held back until they look finished.
- **Be brief.** Lead with the answer, a few sentences, no bullet lists unless
  asked.
- **Don't agree by default.** If a plan is worse than what already exists,
  say so.
- **No fabricated results.** Never invent a metric or an outcome to fill a
  gap. Flag the gap and stop.
